# 카드 혜택 데이터 수집

카드사 약관에서 혜택 규칙을 뽑아 DB에 적재하는 경로다.
카드가 늘어날 때 코드를 고치지 않고 데이터만 추가하기 위한 구조다.

## 단계

```
카드사 문서 (PDF · HTML)
   ↓ extract     텍스트 추출. 실패하면 페이지 이미지 → 비전 모델
원문 텍스트  ─────────────→ card_term_document 에 저장 (원문 + source_url + content_hash)
   ├─ structure   중간 JSON 으로 구조화        ┐ 혜택 규칙 (금액 계산용)
   │  out/*.json                              │
   │  ↓ review    사람이 _needs_review 확인     │
   │  ↓ load      INSERT SQL 생성              ┘
   │  backend/db/91_seed_card_benefit.sql
   │
   └─ chunk       조문 단위로 자름              ┐ 약관 원문 (챗봇 Q&A용)
      ↓ embed     조각을 벡터로 (선택)          ┘
      card_term_chunk
```

각 단계가 독립이라 재실행된다. 스키마가 바뀌면 `structure`부터,
약관이 개정되면 `extract`부터 다시 돌린다.

**갈래가 둘인 이유는 답할 수 있는 질문이 다르기 때문이다.** 왼쪽은 약관에서 뽑아낸
수치라 금액 계산에 쓰이고, 오른쪽은 원문 그대로라 "분실하면 어떻게 하나" 같은
규정 질문에 쓰인다. 한쪽으로 다른 쪽을 대신할 수 없다 — 원문에서 금액을 계산할 수 없고,
컬럼으로 분실 처리 절차를 담을 수 없다.

## 실행

```
python -m ingest.run              수집 → card_term_document   (카드사 사이트를 때린다)
python -m ingest.build_chunks     조문 단위로 자름 → card_term_chunk
python -m ingest.build_embeddings 조각에 임베딩 (API 키 필요, 없어도 검색은 동작)
python -m ingest.seed             혜택 시드 SQL 생성
```

`run` 만 네트워크를 쓴다. 자르는 규칙을 고쳤을 때는 `build_chunks` 만 다시 돌리면 된다 —
원문이 DB 에 있어 카드사 사이트를 다시 받지 않는다.

## 문서가 카드 단위만 있는 것이 아니다

| 유형 | 무엇 | 답할 수 있는 것 |
|---|---|---|
| `PRODUCT_GUIDE` · `KEY_TERMS` | 카드별 상품설명서·주요거래조건 | 혜택·연회비·실적 조건 |
| `MEMBER_TERMS` | **카드사별 개인회원 약관** | 분실·도난·해지·이의제기 |

카드별 문서에는 분실·도난 조항이 거의 없다(카드 15장 통틀어 3건). 그 내용은 카드사 단위
개인회원 약관에 있고, 카드가 몇 장으로 늘어도 카드사마다 문서 수는 그대로다.

수집 대상은 두 파일에 나눠 적는다 — `selection.json`(카드), `member_terms.json`(회원약관).
고르는 기준이 달라서다. 카드는 카드 이름으로 거르는데 회원약관은 카드와 무관해
같은 기준을 태우면 통째로 걸러진다.

## 중간 JSON 이 계약이다

`out/*.json` 형식이 이 파이프라인의 계약이다. 앞단(수집)이 무엇으로 바뀌든
이 형식으로 들어오면 뒷단(검수·적재)은 그대로 동작한다.

원천을 바꾸는 일은 **수집 어댑터 교체 하나**로 끝난다.
데이터 중계사의 표준 API를 쓰게 되면 `그 응답 → 중간 JSON` 매핑만 추가하면 된다.

## 문서 형태가 카드사마다 다르다

실제로 확인한 것들이다.

| 문서 | 추출 |
|---|---|
| 상품설명서 (일부) | 페이지 전체가 이미지. 텍스트 추출 불가 → 비전 모델 필요 |
| 신용카드 설명서 / 주요거래조건 | 텍스트 추출 가능. 혜택 요약·제외 대상·실적 기준이 모두 들어 있음 |
| 개인회원 약관 (신한·삼성) | **PDF 가 아니라 웹페이지 본문.** 조문 구조가 살아 있어 오히려 다루기 쉽다 |

그래서 `extract`는 **텍스트 추출을 먼저 시도하고, 실패하면 비전으로 폴백**한다.
PDF 인지 HTML 인지는 **바이트 앞머리로 판정한다** — 카드사가 PDF 주소라고 해놓고
오류 페이지를 HTML 로 돌려주는 일이 있어, 선언된 형식을 믿으면 빈 원문이 정상처럼 저장된다.

한 화면에 지난 시행본이 함께 실린 카드사가 있다(삼성, 시행일 4개 버전). 최신본만
펼쳐져 있고 나머지는 숨김이라, **화면에 보이는 블록만 남긴다.** 통째로 넣으면 몇 해 전
조항이 검색에 걸려 지금은 틀린 답이 나간다.

## 검수 규칙

약관에 명시되지 않은 값을 임의로 채우지 않는다. 대신 표시해서 사람이 보게 한다.

| 표시 | 의미 |
|---|---|
| `_source` | 이 값이 나온 약관 문장 |
| `_needs_review` | 약관에 없어 판단이 필요한 필드 |
| `unmapped` | 스키마로 표현하지 못한 조항 (원문 보관) |

숫자 전체를 대조하는 대신 이 세 가지만 확인하면 된다.
자동 추출은 초안을 만들 뿐이고, DB에 들어가는 값은 사람이 확인한 값이다.

## 폴더

```
raw/      원본 PDF (커밋 제외 — 저작권. source_url 로 재취득)
out/      중간 JSON (커밋) + 페이지 렌더링 PNG (커밋 제외)
```

## 실행 환경

파이썬 배치 스크립트다. 챗봇 서버와는 별개 프로세스이며 상시 실행되지 않는다.
계산 엔진(Java)은 적재된 결과만 읽고, 수집 로직을 갖지 않는다.
