# 카드 혜택 챗봇 서버

카드·혜택 질문에 답하는 별도 프로세스다. Spring(WAR)과 같은 서버에 뜨지 않고 REST 로 통신한다.

## 호출 경로

```
프론트 ──▶ Spring  POST /api/chat        JWT 검증 · 회원 id 확보 · 토큰 전달
             │
             ▼
          Python  POST /chat
             ├─ ① classify   말 → 의도 + 언급된 표현              ← LLM
             ├─ ② resolve    표현 → 가맹점·카드·업종 식별          (DB, 별칭 표)
             ├─ ③ 조회       엔진 API 호출                        (Spring 으로 되돌아감)
             ├─ ④ 조립       숫자를 완성된 문자열로
             └─ ⑤ compose    확보한 값 → 문장                     ← LLM
             ▼
          답변
```

**프론트가 이 서버를 직접 부르지 않는다.** Spring 의 JWT 필터가 검증을 끝낸 요청만 넘어오고,
이 서버는 토큰을 다시 열지 않는다. 검증 로직이 두 벌이 되면 서명 방식이나 만료 처리가
한쪽만 바뀌어도 조용히 어긋난다.

③에서 파이썬이 Spring 으로 되돌아간다. ②시점에는 아직 의도 분류 전이라 Spring 이 어떤
데이터를 보내야 할지 모르기 때문이다. 응답 시간의 대부분은 LLM 대기이고(호출 두 번)
localhost 왕복은 밀리초 단위다.

## 판단과 계산은 LLM 이 하지 않는다

LLM 은 **말을 알아듣는 자리**와 **문장을 쓰는 자리** 둘뿐이다. 그 사이는 전부 서버다.

- **금액은 엔진 API 에서 받는다.** 파이썬이 SQL 로 다시 구하면 묶음 한도·구간별 개별 한도
  규칙이 두 곳에 생겨 화면 숫자와 챗봇 숫자가 갈린다
- **숫자는 완성된 상태로 넘긴다.** 천 단위 쉼표까지 서버가 찍는다 — LLM 에게 산수는 물론
  자릿수 맞추기도 시키지 않는다
- **엔티티 표현을 LLM 이 고치지 못하게 한다.** "스벅"을 "스타벅스"로 바꿔 주면 서버가 원래
  표현을 잃고, "이마트24"를 "이마트"로 고치면 편의점이 대형마트가 된다

## 답하는 질문 (의도)

| 의도 | 예 | 쓰는 엔진 API |
|---|---|---|
| `CARD_STATUS` | 실적 채웠어? / 목표 얼마나 채웠지? | `GET /api/cards/monthly-status` |
| `RECOMMEND_CARD` (금액 있음) | 스벅에서 8000원 쓸건데 | `POST /api/recommendations` |
| `RECOMMEND_CARD` (금액 없음) | 스벅에서 어느 카드가 좋아? | `GET /api/cards/applicable-benefits` |
| `BENEFIT_SUM` | 이번 달 얼마 아꼈어? | `GET /api/benefits/report` |
| `TERM_QA` | 카드 잃어버리면? | 없음 — `card_term_chunk` 를 직접 읽는다 |
| `UNKNOWN` | 그 외 | 되묻는다 |

**금액 유무로 갈리는 것이 핵심이다.** 금액을 정해 묻는 사람은 결제 화면에서 추천을 받는다.
챗봇에 오는 "여기서 뭐가 좋아?"는 금액이 없는 것이 정상이고, 답도 순위가 아니라
혜택의 조건(적립률·실적조건·건당 최소금액)이어야 한다.

## 약관 질문만 DB 를 직접 읽는다

금액·한도는 엔진 API 로 받지만 약관은 다르다. 계산 규칙이 아니라 텍스트라 두 곳에서
규칙이 갈릴 위험이 없고, 엔진이 내려줄 수 있는 모양도 아니다.

```
질문 ─classify(LLM)─▶ 약관 낱말      "잃어버렸어요" → "분실 도난 신고"
     ─임베딩 검색───▶ 조문 조각      card_term_chunk.embedding (코사인 유사도)
     ─compose(LLM)─▶ 문장
```

찾은 조문은 **요약하지 않고 그대로 싣는다.** 약관은 단서 한 줄이 결론을 뒤집는데,
줄이면 그 요약이 맞는지 아무도 확인할 수 없다.

유사도가 낮으면 못 찾은 것으로 보고 **없다고 말한다.** 하한이 없으면 어떤 질문에도
뭔가는 걸려서, 무관한 조항을 근거로 그럴듯한 답이 나간다.

### 낱말 검색에서 옮겨온 이유

낱말 검색(ngram FULLTEXT)의 점수는 "뜻이 맞나"가 아니라 **"글자가 얼마나 겹치나"** 였다.
실측에서 뜻이 정반대인 두 질문이 같은 조문을 거의 같은 점수로 집었다.

| 질문 | 낱말 검색 1위 | 임베딩 1위 |
|---|---|---|
| 카드를 잃어버렸어요 | 22.46 분실·도난 신고 | 분실·도난 신고 |
| 카드 없애고 싶은데 | 22.36 **분실·도난 신고** | 신용카드 해지 신청 안내 |
| 연회비 돌려받을 수 있어? | 9.76 (제목없음) | [연회비 반환 기준] |

질문에 '카드'만 들어가면 '카드'가 많이 나오는 조각이 올라오는 구조라, 점수 하한으로
걸러지지도 않았다. 낱말 검색을 후보 추리기로 남기는 안도 재봤으나 질문 셋 중 둘에서
정답이 상위 30건 안에 아예 없어 버렸다.

**말을 약관 낱말로 바꾸는 단계는 그대로 둔다.** 검색어가 약관 어휘에 가까울수록 유사도가
올라가고, 그 일은 표현 추출과 성격이 같아 `classify` 에 얹혀 있어 호출이 늘지 않는다.

### 대가 — 질문마다 임베딩 호출이 는다

| | 낱말 검색 | 임베딩 검색 |
|---|---|---|
| 질문 임베딩 | 없음 | 553~661ms (네트워크) |
| 조각 찾기 | 3~4ms (MySQL) | 0ms (메모리) |
| 유사도 계산 | 없음 | 0.4~0.8ms |

`TERM_QA` 의도에서만 발생하고 다른 질문에는 영향이 없다. 조각은 첫 검색 때 한 번 읽어
메모리에 두므로 **색인을 다시 만들면 챗봇을 재기동해야 한다.**

`EMBEDDING_PROVIDER` 로 공급자를 고른다 — `stub` 은 글자만 보므로 색인·검색 경로를
확인하는 용도이고, 뜻으로 찾으려면 실제 공급자가 필요하다. `GET /health` 의
`embeddingProvider` 로 지금 무엇으로 도는지 확인한다.

## 표현 해석 — 순서가 있다

```
① 정식 명칭 정확 일치  ② 별칭 정확 일치  ③ 표현에 이름이 통째로 들어있음  ④ 되묻기
```

- **①이 ②보다 먼저다.** 정식 명칭은 약관에서 나온 값이라 안 흔들리고, 별칭은 사람이 손으로
  넣어 실수가 들어올 수 있다. 틀릴 수 있는 쪽을 나중에 본다
- **모호한 별칭은 등록하지 않는다** (`GS`·`마이핏`·`컬리`). 못 찾은 것이 되어 되묻는다 —
  조용히 틀린 답을 주는 것보다 낫다
- **③은 LLM 이 조사를 못 뗐을 때의 보험**이다. 후보가 여럿이면 나머지를 문자열로 품는 것만
  고른다("SKT 요금"에 'KT'가 딸려오지만 입력된 이름은 'SKT'다). 서로 안 겹치면 되묻는다
- **매칭 결과를 답변에 노출한다**(`스타벅스 (카페)`). 잘못 잡히면 사용자가 바로 안다

### 별칭 표가 필요한 이유 — LLM 이 대신 못 한다

LLM 은 우리 `merchant` 테이블을 본 적이 없다. **세상의 표기와 우리 DB 표기가 다르다** —
`써브웨이`(서브웨이 아님), `엔제리너스`(엔젤리너스 아님), `SSG.COM`, `농협 하나로마트`.
정규화해 줘도 그 문자열이 DB 에 실재하는지 확인하는 단계는 없앨 수 없고, 별칭이 그 사전이다.

**업종은 예외다.** 팀 표준 40개로 고정이라 목록을 프롬프트에 넣는다. 그러면 "커피" → `카페`,
"지하철" → `대중교통` 매핑이 별칭 없이 된다. 가맹점·카드는 수가 계속 늘어 목록을 줄 수 없다.

## 대화 잇기 (멀티턴)

되물은 뒤 받은 답을 직전 맥락과 합친다. 맥락은 **서버가 보관하지 않고** 응답에 실어 내려준 뒤
다음 요청에 그대로 돌려받는다(`pendingContext`). 보관하면 서버 재시작 때 대화가 끊기고,
여러 대로 늘리면 요청마다 다른 서버로 가 맥락을 잃는다.

맥락을 잇는 경우는 둘로 제한한다 — 이번 분류가 `UNKNOWN` 이거나 직전과 같은 의도일 때다.
주제가 바뀌면 통째로 버려 앞의 가맹점이 따라붙지 않게 한다.

## 실행

```bash
cd ai-server
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r chatbot/requirements.txt   # Windows
# source .venv/bin/activate && pip install -r chatbot/requirements.txt  # macOS/Linux

cp .env.example .env        # 값 채우기
.venv/Scripts/python.exe -m uvicorn chatbot.main:app --reload
```

- API 문서: <http://127.0.0.1:8000/docs>
- 헬스체크: `GET /health` → `{"status":"UP","llmProvider":"stub"}`

> **Spring 이 도커 컨테이너면** 컨테이너에서 호스트의 `127.0.0.1` 에 닿지 못한다.
> 제대로 하려면 챗봇도 같은 도커 네트워크의 컨테이너로 올리고 포트 매핑을 하지 않는다 —
> 그러면 외부 노출 없이 컨테이너끼리만 통한다.

## 개발 중에는 LLM 을 부르지 않는다

`.env` 의 `LLM_PROVIDER` 하나로 갈린다.

| 값 | 동작 | 비용 |
|---|---|---|
| `stub` (기본) | 규칙 기반 가짜 응답 | 0 |
| `openai` | 실제 호출 | 질문 1건당 약 0.5원 (분류+작성) |

stub 은 **등록해둔 표현만** 알아듣는다(`llm/stub.py`). 실제 사용자는 아무 말이나 하므로
**시연 전에는 반드시 `openai` 로 한 번 돌려본다.** `GET /health` 의 `llmProvider` 가
그때 stub 인 채로 들어가는 사고를 막는 장치다.

API 키는 `.env` 에만 둔다. 코드·커밋·발표자료·캡처에 넣지 않는다.

## 프롬프트는 코드가 아니라 파일이다

`prompts/classify.md`, `prompts/compose.md` 에 있다. 프롬프트가 사실상 이 서버의 규칙이라
변경 이력이 diff 로 보여야 하고, 고칠 때 파이썬을 몰라도 되어야 한다.

프롬프트를 고쳤으면 **분류 결과를 재본다.**

```bash
LLM_PROVIDER=openai .venv/Scripts/python.exe -m chatbot.tools.measure_llm
```

17개 표현을 실제 모델과 stub 에 함께 넣어 비교하고, 어느 별칭이 불필요한지도 함께 알려준다.
토큰을 쓰므로 평소에는 돌리지 않는다.

## 테스트

```bash
.venv/Scripts/python.exe -m pytest chatbot/tests -q
```

LLM 은 stub, 엔진은 가짜라 네트워크도 비용도 들지 않는다. 표현 해석만 진짜 DB 를 쓴다 —
별칭 조회가 SQL 안에 있어 가짜로 바꾸면 정작 확인하려는 것을 못 본다. DB 가 없으면 건너뛴다.

## 폴더

```
chatbot/
  main.py          FastAPI 앱·라우팅·맥락 병합
  config.py        .env 로딩 (설정을 읽는 유일한 곳)
  schema.py        Spring 과 주고받는 형식
  db.py            MySQL 연결 (별칭·이름 조회 전용)
  resolver.py      표현 → 가맹점·카드·업종 식별자
  engine.py        엔진 API 호출
  router.py        의도별 조회 + 컨텍스트 조립
  llm/
    base.py        어댑터 계약 (LlmClient, Intent, Answer)
    stub.py        개발용 가짜
    openai_client.py
  prompts/         프롬프트 원문
  tools/           가끔 손으로 돌리는 측정 도구
  tests/
```
